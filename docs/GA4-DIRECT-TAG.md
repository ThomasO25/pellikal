# GA4-DIRECT-TAG.md

The Google tag moved from "inside GTM" to "installed directly by the page" on
**7 October 2026**. GTM (`GTM-MK2PHWB`) stays on every tracked page for
everything else.

**Status: built and verified locally. NOT published. NOT verified against
Google's live endpoints or the live GTM container — see §7.**

---

## 0. The four IDs and what each one is

| Role | ID | Where it lives |
|---|---|---|
| **Google tag installed on the page** (the loader + `gtag('config')`) | **`AW-859941989`** | `site.config.json` → `analytics.googleTagId`; stamped by `tools/build.py` |
| **GA4 Measurement ID / Analytics destination** of that tag | **`G-J8SQ4CC7BT`** | `analytics.ga4MeasurementId`; the GTM tag `GA4 - Pellikal Custom Events`; the privacy policy. **Never a loader ID on the pages.** |
| **GTM container** | `GTM-MK2PHWB` | `analytics.gtmContainerId`; stamped by the build |
| **Google Ads conversion ID** (conversion fires inside GTM on `generate_lead`) | `AW-859941989` | `analytics.googleAdsId`; the conversion label lives in GTM only |

This account uses a **unified Google tag**: the Ads ID is the tag that is
installed, and the GA4 web stream is a connected *destination* of it. That is
exactly what GA4 shows under **Admin → Data streams → Pellikal → View tag
instructions → Install manually**:

```html
<script async src="https://www.googletagmanager.com/gtag/js?id=AW-859941989"></script>
<script>
  window.dataLayer = window.dataLayer || [];
  function gtag(){dataLayer.push(arguments);}
  gtag('js', new Date());
  gtag('config', 'AW-859941989');
</script>
```

Live testing confirmed the other direction does not work in this account:
`gtag/js?id=G-J8SQ4CC7BT` → **404** from Google. The first version of this
change (v25) loaded the G- ID directly; v26 corrects it to the ID Google
itself instructs. `G-J8SQ4CC7BT` is **not** the installed loader ID — it is
the destination that receives the `page_view` the installed tag sends.

## 1. Why the tag moved at all

| | Apex Lift Solutions (direct gtag.js) | Pellikal (GA4 via a Google Tag inside GTM) |
|---|---|---|
| Google tag loader | 200 | **`net::ERR_BLOCKED_BY_CLIENT`** on the `gtag/js?id=G-…` request GTM initiated |
| `/g/collect` page_view | 204 | never generated outside GTM Preview |
| GTM, Consent Mode, Conversion Linker, `generate_lead`, Ads conversion | — | all working |

`ERR_BLOCKED_BY_CLIENT` is the browser refusing a request; and the
`gtag/js?id=G-J8SQ4CC7BT` URL answers 404 in this account anyway. The
page-level install uses the ID that Google's own instructions give.

## 3. The head, in execution order

All three pieces are generated by `tools/build.py` → `gtm_head()` into the
single `<!-- @partial:gtm-head -->` region, so they cannot be reordered by
hand and a rebuild always restores them:

```
 1. window.dataLayer exists                       ┐
 2. window.gtag exists                            │ Consent Mode v2 block
 3. gtag('consent','default', {…denied…, region:[EEA+GB+CH]})   (unchanged, v24)
 4. gtag('consent','default', {…granted…})        │
 5. gtag('set','ads_data_redaction', true)        │
 6. saved Accept/Reject → gtag('consent','update', …)   synchronous   ┘
 7. <script async src="https://www.googletagmanager.com/gtag/js?id=AW-859941989">
 8. gtag('js', new Date()); gtag('config','AW-859941989')   ← guarded (see below)
 9. GTM container snippet (GTM-MK2PHWB) → gtm.start                     (unchanged)
```

Lines 7–8 are Google's snippet from §0 **minus** its two middle lines
(`window.dataLayer = …` and `function gtag(){…}`), which are intentionally
absent because the consent block already created both. One dataLayer, one
`gtag()`, one consent implementation. `gtag.js` loads asynchronously, but what
matters is the *queue*: by the time it executes, the dataLayer already holds
the regional defaults, any saved choice, and then the config — in that order
— and it replays them in order. The installed tag therefore gets exactly the
consent guarantees GTM's Google Tag had: `ads_data_redaction` and the three
ad signals govern its Ads destination, `analytics_storage` its GA4
destination.

The config is wrapped in
`if (window.PELLIKAL_CONSENT_SETTINGS && typeof window.gtag === 'function')`.
`PELLIKAL_CONSENT_SETTINGS` is the first statement of the consent block, so if
that block were ever missing from a page, the Google tag would simply **not be
configured** there instead of running on Google's implicit "granted".

**Exact generated snippet** (as stamped into every tracked page):

```html
<script async src="https://www.googletagmanager.com/gtag/js?id=AW-859941989"></script>
<script>
if(window.PELLIKAL_CONSENT_SETTINGS&&typeof window.gtag==='function'){
gtag('js',new Date());
gtag('config','AW-859941989');
}
</script>
```

What that one config does: sends the GA4 `page_view` to the connected
destination `G-J8SQ4CC7BT`, and loads the Google Ads tag for `AW-859941989`
(remarketing/page signals, subject to the advertising consent signals). It
sends **no conversion** — there is no conversion label in page code and no
`gtag('event', …)`; the Ads lead conversion still fires only from GTM on
`generate_lead`.

Pages carrying it: the 13 tracked public pages (`/`, residential, commercial,
window-inserts, contact, about, faq, solutions, privacy, terms, accessibility,
`/thankyou/`, `404.html`). Not on `/admin/` or `/local-law-97/`
(`excludeFromTracking`), which carry no Google code at all.

## 5. How the GA4 custom events keep working

The site pushes its events to `window.dataLayer` exactly as before —
`quote_cta_click`, `quote_form_view`, `quote_form_start`, `quote_form_error`,
`click_to_call` / `click_to_text` / `click_to_email`, `contact_form_submit`,
`homepage_form_submit`, `generate_lead`, `window_insert_lead`,
`view_contact_page`, `consent_update`. Nothing was renamed, added or removed
(`js/tracking.js` is behaviour-identical to v24).

> **Naming note:** earlier briefs refer to `phone_click` / `text_click`. The
> site has never pushed events by those names; its dataLayer events are
> `click_to_call` and `click_to_text`. If GA4 shows `phone_click`/`text_click`,
> that renaming happens inside the GTM tag.

They reach GA4 through the existing GTM tag **`GA4 - Pellikal Custom Events`**
(Measurement ID `G-J8SQ4CC7BT`). A GA4 event tag needs a Google tag that
serves that Measurement ID to be loaded on the page. With the unified tag
`AW-859941989` installed, `G-J8SQ4CC7BT` is one of its destinations, so the
event tag should send through that instance. **This is the one thing the
repository cannot prove.** If GTM does *not* recognise the destination as
loaded, it will try to load `gtag/js?id=G-J8SQ4CC7BT` itself — which answers
**404** in this account — and the events would be lost. §7 therefore checks
explicitly, after firing `generate_lead`, that **no** `gtag/js?id=G-J8SQ4CC7BT`
request appears. If one does: **that is a failure; do not publish; report it.**

**Decision rule:** no `gtag('event', …)` has been added to the site. Only if
§7 proves the GTM event tag cannot send through the unified tag does a direct
event bridge become an option — and then the GTM event tag would have to be
paused at the same time, never both. Duplicate custom events are worse than a
short gap.

## 6. GA4 property settings to verify (manual, in the GA4 admin)

Nothing below is code. **Do not hand-code events that Enhanced Measurement
already provides.** GA4 → Admin → Data streams → *Pellikal web stream* →
Enhanced measurement:

| Option | Setting | Why |
|---|---|---|
| Page views | **ON** (required) | the `page_view` the installed tag sends to the GA4 destination |
| Scrolls | **ON** | `scroll` at 90 % depth — the "scroll" metric in the goals list |
| Outbound clicks | **ON** | `click` with `link_url` for links leaving the site (Indow, LLumar, etc.) |
| Site search | leave default | no site search on pellikal.com; nothing triggers it (`?service=` / `?consent=reset` are not search parameters) |
| Video engagement | leave default | no embedded YouTube players |
| File downloads | leave default | no downloadable files |
| **Form interactions** | **OFF** | GA4 would emit its own `form_start`/`form_submit` for the quote form — `form_submit` fires on the submit *attempt*, including validation failures and Formspree errors, so it is **not** a lead and would be confused with `generate_lead`. The site's own `quote_form_start` / `quote_form_error` / `generate_lead` are the precise versions. |
| Page changes based on browser history events | leave default | static multi-page site; not applicable |

Also in GA4 admin:

- **Admin → Events → mark `generate_lead` as a Key event.** It is the
  successful-form signal. Do **not** mark `page_view` of `/thankyou/`,
  `contact_form_submit`, `click_to_call` or `click_to_text` as key events —
  those are diagnostics (the Google Ads conversion stays separate, in GTM, on
  `generate_lead`).
- **Admin → Custom definitions → event-scoped custom dimensions:**
  `form_location`, `cta_location`, `error_type`, `service`, `lead_source`,
  `page_type`, `click_location`. Without these the parameters are collected
  but never appear in reports.
- **Data retention:** 14 months (Admin → Data settings → Data retention).
- **Google signals:** an owner decision, not required for any goal below.
- No PII is collected by any of this: the site pushes no names, phone
  numbers, email addresses or ZIPs to the dataLayer (verified by both suites),
  and Enhanced Measurement never reads field values.

### Where each goal is read (standard reports unless noted)

| Goal | Where |
|---|---|
| active users, new users, sessions | Reports → Life cycle → Acquisition → *Overview* / *User acquisition* |

| phone / text clicks | Engagement → *Events* → `click_to_call`, `click_to_text` (or the names the GTM tag maps them to — see §5) |

## 8. Risks of duplicate tracking

| Risk | Effect | Guard |
|---|---|---|
| GTM Google Tag `GA4` un-paused while the direct tag is live | 2× `page_view`, sessions/engagement/bounce wrong | §4; build summary reminder; §7 counts hits |
| GTM GA4 event tag tries to load `gtag/js?id=G-J8SQ4CC7BT` itself | 404 → custom events lost (not duplicated) | §7 "no second loader" check — failure if seen |
| a separate Google Ads *Remarketing* tag on all pages in GTM | two Ads page signals per page (the page's Google tag already sends one) | not in the listed active tags; check the container when auditing |
| Enhanced Measurement *Form interactions* on | `form_submit` fires on failed attempts too; looks like a lead | §6: OFF |
| `page_view` of `/thankyou/` treated as a conversion / key event | counts refreshes and revisits as leads | never a trigger (LEAD-FLOW.md); key event is `generate_lead` only |
| a `gtag('event', …)` added to page code **and** the GTM event tag kept | every custom event twice | none added; decision rule in §5 |
| a conversion label (`AW-859941989/…`) pasted into page code | the Ads conversion counted by the page *and* by GTM | the suites fail the build on `AW-…/` or `'conversion'` in any page |
| legacy `GA4 Event - Contact Form Fill` un-paused | thank-you page view double-reported | keep paused (§4) |

## 9. Rollback

1. `site.config.json` → `"ga4DirectTag": false`.
2. `python3 tools/build.py` (twice; second run `Pages updated: 0`). The loader
   and the config disappear from every page; nothing else changes.
3. Publish the site.
4. In GTM, un-pause the Google Tag `GA4` (`G-J8SQ4CC7BT`) and publish the
   container.

Do 3 before 4 (a brief gap with no page views is harmless; an overlap counts
twice). Both QA suites run clean in either mode — the checks read
`ga4DirectTag` and assert "exactly one direct tag, `AW-859941989`" or "no
direct tag" accordingly.
