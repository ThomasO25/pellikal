# CONSENT-MODE.md

Google Consent Mode v2 on pellikal.com — what it does, how to verify it,
and how to reset it for testing.

**Added:** 14 September 2026 · **v2 (granular categories) same day**

---

## The one thing that matters

A consent *default* only counts if it is set **before** `gtm.js` loads. Set it
afterwards and Google has already been running on its implicit "granted" for
the first hit of every page — which is exactly the situation this replaces.

So the defaults are **not** in a normal script file. They are an inline block
at the very top of every tracked page's `<head>`, generated by
`tools/build.py` as part of the same function that emits the GTM snippet:

```
<head>
  <meta charset="utf-8">
  <!-- @partial:gtm-head -->
    ... Consent Mode v2 defaults ...   <-- generated, first
    ... Google Tag Manager snippet ...  <-- generated, second
  <!-- @end -->
```

They live in one generated region on purpose. Nobody can reorder them by
hand, and a rebuild always restores both.

---

## What the defaults are

| Category | Default | Why |
|---|---|---|
| `ad_storage` | **denied** | optional |
| `analytics_storage` | **denied** | optional |
| `ad_user_data` | **denied** | optional |
| `ad_personalization` | **denied** | optional |
| `functionality_storage` | granted | the site has to work |
| `security_storage` | granted | anti-fraud / security |

Plus `ads_data_redaction: true` while denied, which tells Google Ads to
redact ad-click identifiers in its cookieless pings. It is switched off
automatically the moment a visitor accepts.

**`url_passthrough` is deliberately OFF.** It would thread the `gclid` through
internal links when consent is denied. It is privacy-*decreasing*, so it is not
enabled quietly. Turn it on only as a deliberate, recorded decision.

**There is no `wait_for_update`.** Google recommends it when a stored choice is
restored asynchronously. Here it is restored synchronously in the same head
block, so there is nothing to wait for — adding it would delay every tag by
half a second for no benefit.

## Accept / decline behaviour

| | `ad_storage` | `analytics_storage` | `ad_user_data` | `ad_personalization` |
|---|---|---|---|---|
| Before any choice | denied | denied | denied | denied |
| **Accept All** | granted | granted | granted | granted |
| **Reject Non-Essential** | denied | denied | denied | denied |
| Manage → **Analytics only** | denied | **granted** | denied | denied |
| Manage → **Advertising only** | **granted** | denied | **granted** | **granted** |

Analytics maps to `analytics_storage` alone. Advertising maps to the three ad
categories together. They are never tied to each other internally. Nothing is
pre-selected; a reopened dialog shows the visitor's *current* saved choice.

Every save sends an explicit `update`, even when everything stays denied, so
the decision is visible in Tag Assistant rather than looking unanswered. The
`consent_update` dataLayer event carries `consent_choice`
(`accept_all` / `reject` / `custom` / `reset`), `consent_analytics` and
`consent_advertising`.

## Where the choice is stored

A first-party cookie, mirrored to `localStorage` in case cookies are refused:

```
pellikal_consent = v2:a1:d0:2026-09-14     # analytics on, advertising off
pellikal_consent = v2:a0:d0:2026-09-14     # rejected
```
`a` = analytics flag, `d` = advertising flag. v1 values (`v1:all…`) no longer
match and those visitors are asked again — that was the point of bumping.

`Path=/`, `SameSite=Lax`, `Secure` on HTTPS, 180 days.

Four fields: version, analytics, advertising, date. **No personal data, ever.** The version
prefix is how you re-ask everyone — bump `version` in `site.config.json` and
every stored choice stops matching.

A returning visitor's choice is re-applied **in the head, before GTM**, so
someone who accepted is not measured as denied on the first hit of each page.

## How a visitor changes their mind

- **Tracking preferences** button in the footer of every page — opens the
  preferences dialog (role=dialog, focus contained, Escape = close without
  change, focus returned to the button)
- the same control inline in the privacy policy
- `?consent=reset` on any URL — clears the choice and brings the banner back,
  then removes itself from the address bar

The footer/privacy controls stay hidden unless `js/consent.js` is running
(`html.consent-ready`), so nobody is shown a button that cannot do anything.

## Verifying in Tag Assistant

1. Open `https://www.pellikal.com/?consent=reset` (or clear the
   `pellikal_consent` cookie).
2. Tag Assistant → **Connect** → load the page.
3. Open the **Consent** tab and read the **On-page Default** column.

| Step | Expect |
|---|---|
| Before choosing | all four optional = **denied** |
| Click **Accept All** | an *Update* row, all four = **granted** |
| Reset, click **Reject Non-Essential** | an *Update* row, all four still **denied** |
| Reset, Manage → Analytics on → Save | `analytics_storage` granted, three ad categories denied |
| Navigate to another page after accepting | default denied, then an immediate update to granted, **both before** the `Container Loaded` event |

That last row is the important one. If the update appears *after*
`Container Loaded`, the head block is not running first and something has been
edited by hand.

Also check the **Variables** tab on any tag: `Consent State` should match.

## Resetting for testing

| Method | How |
|---|---|
| URL | add `?consent=reset` to any page |
| Console | `PELLIKAL_CONSENT.reset()` |
| By hand | delete the `pellikal_consent` cookie **and** the `localStorage` key |
| Everyone at once | bump `analytics.consent.version` in `site.config.json`, rebuild |

Other console helpers: `PELLIKAL_CONSENT.get()` returns
`{analytics, advertising}` or `null`; `.acceptAll()`, `.rejectAll()`,
`.save({analytics:true, advertising:false})`, `.open()`, `.reset()`.

## If it breaks

**Banner never appears** — a choice is already stored. Use `?consent=reset`.

**Banner appears on every page** — the cookie is not being written. Check you
are on `http(s)://` and not `file://`, and that `Path=/` was not changed.

**Tag Assistant shows granted before any choice** — the head block is missing
from that page. Run `python3 tools/build.py`.

**Console warns "Consent Mode defaults are missing from `<head>`"** — same
cause. `js/consent.js` sets the defaults late as a safety net, but late is not
the same as correct. Rebuild.

## Consent Mode does NOT cover tags you add in GTM

This is the part that catches people out, and it caught this project out.

Google's own tags (GA4, Ads) read the consent state automatically. **A custom
HTML tag or a third-party template does not.** Microsoft Clarity, a chat
widget, a call-tracking script, a Meta pixel — each one fires on its trigger
regardless of what the visitor chose, unless you tell it otherwise.

A consent banner that does not actually control those tags is worse than no
banner, because the site is then promising something it does not do.

**To gate a tag in GTM:** open the tag → *Advanced Settings* → *Consent
Settings* → **Require additional consent for tag to fire** → add
`analytics_storage` (or `ad_storage` for advertising tags). The tag then waits
for consent and fires only if it is granted.

**The repository cannot see any of this.** `tools/build.py` controls the
container snippet and the defaults; everything inside the container lives in
Google's UI. So an audit of this repo can prove what the *pages* load — it can
never prove what the *container* loads. Anything asserted about GTM contents,
including in the privacy policy, has to be checked in GTM itself.

Practical rule: **the list of tools in `privacy/index.html` is a claim about
the GTM container, not about this repository.** Re-check it in GTM whenever a
tag is added or paused.

| File | Role |
|---|---|
| `tools/build.py` → `consent_head()` | generates the defaults; **the important one** |
| `site.config.json` → `analytics.consent` | cookie name, version, duration, redaction |
| `js/consent.js` | the banner, the update, storage, reopen/reset |
| `css/styles.css` § 16 | banner styling |
| `partials/footer.html` | the footer reopen button |
| `privacy/index.html` | the policy wording and the inline reopen control |

If `js/consent.js` is blocked, the defaults still stand and everything optional
stays denied. The failure direction is always *less* tracking.

## What deny-by-default does to Google Ads measurement (US traffic)

Nothing here is legally required for Nassau/Suffolk/NYC visitors; deny-by-
default is a privacy choice. It has a measurement cost worth knowing:

- Every visitor who has not pressed **Accept All** (or switched Advertising
  on) is measured with `ad_storage: denied`. The Conversion Linker cannot
  write `_gcl_aw`; the Ads conversion tag (fired on `generate_lead`) sends
  a **cookieless** ping, and with `ads_data_redaction: true` Google redacts
  ad-click identifiers from what it sends in that state. `js/main.js`
  forwards `gclid`/`gbraid`/`wbraid` through the redirect (17 Sep 2026) so
  internal navigation never *drops* the identifier — Google warns that
  redirects losing the GCLID break attribution — but this does not override
  the consent state and does not make denied-consent traffic deterministic.
  Expect restricted/modelled measurement for visitors who reject.
- What remains cookieless is subject to Google's consent-mode modelling,
  which needs volume to kick in. At Pellikal's lead counts, expect reported
  Ads conversions to lag actual leads unless visitors accept.
- GA4 with `analytics_storage: denied` sends cookieless pings only: sessions
  and users are modelled, events still arrive. `generate_lead` still counts.

Options if reported conversions stay far below real leads: (a) keep this
setup and rely on click-ID forwarding plus the Formspree inbox as the source
of truth; (b) an owner/legal decision to default `ad_storage` and
`analytics_storage` to **granted** for non-EEA traffic (Consent Mode's
"advanced" pattern), with the banner then acting as an opt-out — that
changes `consent_head()` in `tools/build.py` and the privacy policy wording,
and is not something to do quietly.

## Why there is no GTM `<noscript>` iframe

Google's standard install adds `<noscript><iframe src=".../ns.html?id=…">` so
the container still loads with JavaScript off. On this site the banner *and*
the defaults are JavaScript. A JavaScript-off visitor can never choose and
never receives "denied" — so the iframe would load the container with no
consent state at all, i.e. Google's implicit **granted**. That is the one path
that bypassed everything above, and it was removed on 14 Sep 2026. The
`@partial:gtm-body` region is kept, containing only a comment saying so.
